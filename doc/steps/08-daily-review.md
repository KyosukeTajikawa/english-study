# ステップ8: 毎日10問復習

## 目的

その日の復習10問を選定し、`DailySet` に固定する。途中で離脱しても再開でき、**再訪時に問題が入れ替わらない。**

## 実装方針

### 1. 「その日」の定義（最初に固める）

**このステップで最も間違えやすい部分。**

- 基準は `User.timezone`（既定 `Asia/Tokyo`）
- 日付の区切りは**そのタイムゾーンの 0:00**。UTC の 0:00 ではない
- `DailySet.date` には**タイムゾーン適用済みの `YYYY-MM-DD` 文字列**を保存する

```
getTodayKey(now, timezone) → "2026-09-07"
```

純粋関数にして、**日付境界の前後1分**を含むテストを書く。

Lambda は素の Node.js なので `Intl.DateTimeFormat` の `timeZone` オプションがそのまま使える（Workers と違い懸念なし）。

### 2. セット固定のフロー

```
復習画面を開く
  → getTodayKey() で今日のキーを算出
  → DailySet を (userId, todayKey) で検索
      あり → その questionIds をそのまま使う   ← 再ランダム化しない
      なし → 10問を選定して DailySet を作成
```

`@@unique([userId, date])` を張っているので、同時アクセスで二重作成されても DB が弾く。**一意制約違反を捕捉して「既存を読み直す」フォールバックを入れる。**

### 3. 選定ロジックは再利用する

ステップ6の `selectQuestions` を呼ぶ。**同じ処理を書き直さない（DRY）。**

`build-daily-set.ts` の責務は以下に限定する。

1. 候補となる `Question` を DB から集める（間隔条件で除外、`recentlyServed` も取得）
2. `attemptStats` を集計して取得
3. 候補が不足なら**フォールバック生成**を試みる（下記3-2）
4. `selectQuestions` を呼ぶ
5. 結果を `questionIds` に変換して `DailySet` を作る
6. **★ 選ばれた `Question` の `lastServedAt` を一括更新する**（`DailySet` 作成と同一トランザクション）

> トランザクションが使えるのは **pooled 接続 + WebSocket**（`PrismaNeon`）だから。HTTP ドライバでは `$transaction()` が例外を投げる（ステップ3参照）。接続方式を変えるとここが壊れる。

**6 を忘れると看板機能が壊れる。** ステップ6は「出題が確定した時点で `lastServedAt` を更新する」と定めているが、`DailySet` を作る経路はここしかない。更新しないと全問が `lastServedAt = null` のままになり、(a) 間隔制御が一切効かず、(b) 優先度1「未出題」に全問が該当し続けて**翌日も同じ問題が最優先で選ばれる**。同日再訪しか見ない E2E では気づけない。

**選定ロジック自体のテストはステップ6側に集約する。** ここで重複したテストを書くと、片方だけ直したときに気づけない。

### 3-2. ★ 候補0件の分岐（初日の体験）

候補が0件になる原因は2つあり、**取り違えると初回利用時に誤った案内を出す。**

| 状況 | 対応 |
| --- | --- |
| `Vocabulary` が0件 | 単語登録への導線を返す |
| **単語はあるが `Question` が0件** | `generateQuestionsForVocabulary()` をフォールバック呼び出し（ステップ6）。予算・生成数の上限内で |
| 生成してもなお0件 | 「問題を用意できませんでした」を返す |

**夜間バッチはステップ9で初めて動くため、アプリを初めて使った日は必ず2番目の状態になる。** すでに単語を登録した人に「単語を登録しましょう」と表示するのは明確な誤り。

候補が10問に満たない場合は**あるだけ返す**（エラーにしない）。

なお `MAX_QUESTIONS_PER_VOCABULARY_PER_SET = 3` のため、**登録単語が3件以下だと構造上10問に届かない。** 破綻はしないが、画面に「単語をもう少し登録すると10問になります」と理由を表示して落差を吸収する。

### 3-3. ★ レスポンスの形（正解を漏らさない）

ステップ7は「出題 API に `answer` と `explanation` を含めない」と定めた。一方このステップは「解答済みは結果のみ表示、再解答不可」を既定とする。**この2つが衝突する。**

再開時に解答済み問題の結果を出すには正解と解説が要るが、**未解答の問題まで一緒に返すと、まだ解いていない9問の答えが最初のレスポンスで丸ごとブラウザに渡る。** ステップ7で作った防御が無効化される。

レスポンスを2つに分ける。

```
{
  questions: QuestionForClient[],     // answer と explanation を持たない型
  results: {                          // Attempt が存在する問題のみ
    [questionId]: { isCorrect, correctAnswer, explanation }
  }
}
```

`results` に入れるのは**実際に解答済みの問題だけ**。未解答の問題は絶対に含めない。

### 4. 進捗と再開

進捗は `DailySet.questionIds` と、**`dailySetId` が一致する `Attempt`** の突き合わせで導出する。

**`dailySetId` で絞ることが重要。** 単に「その日の `Attempt`」で判定すると、自由学習で解いた問題が復習の進捗を汚染し、解いていないのに解答済み扱いになる。ステップ3で `Attempt.dailySetId` を用意してあるのはこのため。

- 進捗を別カラムで二重管理しない。`Attempt` が唯一の真実
- 未解答の最初の問題から再開する
- 全問解答済みなら完了画面

### 5. 解答済み問題の再表示

**「解答済みは結果のみ表示、再解答不可」を既定とする。** 履歴の整合が取りやすい。

### 6. 存在しない問題の除外

セット作成時に存在した問題が、後で単語ごと削除される可能性がある。**セット読み出し時に存在しない `questionId` を除外する。**

`Vocabulary` は論理削除なので `Question` 自体は残るが、削除された単語の問題を出し続けるのは不自然。読み出し時に `deletedAt: null` の単語に紐づく問題のみに絞る。

## テスト

**先に書く（RED）:**

`date.ts`（最重要）

- `Asia/Tokyo` で 23:59 と翌 00:01 が別の日になる
- UTC 深夜が日本時間では翌日になる
- タイムゾーンが変わると結果が変わる

`repositories/daily-set.ts`

- **同日2回目の呼び出しで同じ questionIds が返る**（最重要）
- 一意制約違反時に既存を読み直す

`build-daily-set.ts`

- **`DailySet` 作成時に、選ばれた問題の `lastServedAt` が更新される**（最重要）
- **翌日の選定で、前日出した問題が間隔条件により候補から外れる**
- `Vocabulary` が0件 → 単語登録の導線を返す
- **単語ありかつ `Question` 0件 → フォールバック生成が呼ばれる**
- 生成してもなお0件 → 「用意できませんでした」を返す
- 削除された単語の問題が除外される

レスポンス形状

- **未解答の問題に `answer` / `explanation` が含まれない**
- 解答済みの問題のみ `results` に入る

進捗の導出

- **別の `dailySetId` の `Attempt`（前日のセット等）が今日の進捗に混入しない**
- 3問解答済みなら4問目から再開する

**E2E:**

- 3問解いて離脱 → 再訪で同じセットの4問目から再開
- 10問解き切ると完了画面
- 同日に再読み込みしても問題が変わらない

## 注意点

- **「未定着」の判定基準**（何回正解したら定着とみなすか）を定数化し、ドキュメントに残す
- `DailySet.questionIds` は PostgreSQL の JSON 型。読み出し時は Zod で検証し、壊れていたら再生成する
- `date.ts` はステップ9の通知スケジュール判定でも使う。**同じ関数を共有する**（DRY）
